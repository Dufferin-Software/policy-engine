# TPM Usage in policy-node-agent

This document describes when the agent uses a TPM, what is stored inside it, and how the TPM-backed identity fits into the broader fleet security architecture. For the full enrollment and mTLS flow see [enrollment-crypto.md](enrollment-crypto.md).

---

## When the TPM Is Used

The agent selects its identity backend at runtime, with no build-time feature flag:

1. Check for a TPM 2.0 device node at `/dev/tpmrm0` (resource manager, preferred) or `/dev/tpm0` (direct).
2. If present, attempt `TpmNodeIdentity::load_or_create()`. On success the TPM backend is used for the rest of the process lifetime.
3. If the TPM is present but unusable (busy, permission denied, owner hierarchy locked out, library error), log a warning and fall through.
4. Otherwise use `FileNodeIdentity` backed by `/var/lib/policy-node-agent/identity.key` (PKCS#8 PEM, mode 0600).

This means a host with a TPM transparently upgrades to hardware-backed identity, and a host without one continues to work with a file-based key. There is no separate configuration knob.

Whether the TPM is in use on a given node is exposed via the `tpm_backed` label on the `fleet_node_info` Prometheus metric and via `NodeIdentity::tpm_available()` in the agent.

**Source:** `fleet/agent/src/identity/mod.rs:64-86`, `fleet/agent/src/identity/tpm.rs:16-19`

## What Is Stored in the TPM

Exactly one thing: the **node identity signing key**.

- Algorithm: ECDSA P-256, signing scheme `EcDsa(SHA-256)`.
- Created with `fixed_tpm`, `fixed_parent`, and `sensitive_data_origin` set — the private key is generated by the TPM's RNG and cannot be exported.
- Persisted at owner-hierarchy handle **`0x81000001`** so the same key (and therefore the same node ID) survives reboots, agent restarts, and package upgrades.
- Created under a restricted ECC storage primary in the Owner hierarchy. The primary is recreated on demand from the owner seed; only the leaf signing key is `evict_control`'d into persistent NV space.

Nothing else lives in the TPM. In particular:

| Item | Stored in TPM? | Where it lives |
|---|---|---|
| Node identity private key | **Yes** (handle `0x81000001`) | TPM NV |
| Node identity public key | No (derived from TPM on demand) | — |
| mTLS client private key (`controller-client.key`) | No | `/var/lib/policy-node-agent/` mode 0600 |
| mTLS client certificate | No | `/var/lib/policy-node-agent/` |
| Controller CA certificate | No | `/etc/policy-node-agent/controller-ca.crt` |
| Enrollment ephemeral CSR key | No (generated per-enrollment, discarded) | memory |
| PCR-bound seals, attestation keys | Not currently used | — |

**Source:** `fleet/agent/src/identity/tpm.rs:142-264`

## How It Fits the Security Architecture

The fleet uses a deliberate **two-key model** (see `enrollment-crypto.md`):

- **Identity key** — long-lived, stable, the basis of `node_id = hex(SHA-256(SPKI DER))`. Used only to prove possession during enrollment and never directly for TLS.
- **mTLS client key** — issued by the controller on approval, rotated on re-enrollment, used for the ongoing management channel.

The TPM backs only the identity key. The benefits flow through the architecture as follows:

1. **Node ID is bound to the hardware.** Because the private key cannot leave the TPM, no one can copy `identity.key` off a node and impersonate it on a different host. A cloned VM image without the original TPM cannot reproduce the node ID.
2. **Enrollment proof-of-possession is hardware-attested.** The ECDSA signature over `SHA-256(csr_pem)` in `EnrollmentRequest` is produced by the TPM (`tpm_sign`), so the controller knows the request originated from a host that physically possesses the key.
3. **Stability across reinstalls.** Reinstalling the agent package or wiping `/var/lib/policy-node-agent/` does not change the node ID — the persistent TPM handle is the source of truth. The agent re-derives the public key (and node ID) from the TPM on every start.
4. **The mTLS key remains software.** Today the controller generates the mTLS keypair on approval and ships `key_pem + cert_pem` to the agent. This is a deliberate tradeoff: simpler controller-side rotation at the cost of the mTLS key not being TPM-bound. A future phase will optionally accept an agent-submitted CSR for a TPM-resident mTLS key so that the credential used on the wire also never leaves hardware (see `enrollment-crypto.md` Phase 5).

The threat model assumption is therefore: an attacker with root on the host can read the mTLS key and impersonate the node *until the cert expires or is revoked*, but cannot extract the identity key and cannot produce a fresh enrollment under that node ID on different hardware.

## Operational Notes

- **Permissions.** The agent must be able to open the TPM device node. On Debian/Ubuntu the `tss` group typically owns `/dev/tpmrm0`; either run the agent as a user in that group or grant access via udev. Containers must bind-mount `/dev/tpmrm0` into the container if TPM-backed identity is desired.
- **Owner hierarchy auth.** The code uses an empty owner auth value and a password session. If the operator has set an owner password (`tpm2_changeauth -c owner`), `CreatePrimary`/`EvictControl` will fail with a TPM auth error and the agent will fall back to the file backend with a warning.
- **Handle collisions.** Handle `0x81000001` is in the standard owner-hierarchy persistent range (`0x81000000`–`0x817FFFFF`). If another application has already claimed this handle, key creation will fail; the agent currently does not search for an alternate handle.
- **Decommissioning a node** does not need to clear the TPM. Revocation is handled at the controller (`revoked_certs` table) and at the application layer (`NodeStatus`). To fully reset a node's identity, evict the persistent handle with `tpm2_evictcontrol -c 0x81000001` and remove `/var/lib/policy-node-agent/identity.key`; the next agent start will create a new key and produce a new node ID.
- **Observability.** `fleet_node_info{tpm_backed="true"|"false"}` lets dashboards and alerts distinguish hardware-backed from file-backed nodes across the fleet.
