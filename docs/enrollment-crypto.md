# Enrollment and Post-Enrollment Security

This document describes the cryptographic mechanisms used during agent enrollment and the security of the ongoing management channel between `policy-node-agent` and `policy-controller`.

---

## Actors and Key Material

| Actor | Key | Algorithm | Generated by | Location |
|---|---|---|---|---|
| Controller CA | CA signing key | ECDSA P-384 | Controller (first boot) | `ca.key` |
| Agent | Identity key | ECDSA P-256 | Agent (first boot) | `/var/lib/policy-node-agent/identity.key` |
| Node (post-enrollment) | mTLS client key | ECDSA P-256 | Controller (on approval) | `/var/lib/policy-node-agent/controller-client.key` |
| Controller | gRPC server cert key | ECDSA P-256 | Controller (each boot) | in-memory |

All private key files are written with mode **0600**. All TLS is implemented via **rustls** backed by the **ring** cryptographic provider (no OpenSSL dependency).

---

## Phase 0: Controller CA Bootstrap

On first start the controller checks for `ca.key` and `ca.crt` on disk. If absent it:

1. Generates a fresh **ECDSA P-384** keypair (`rcgen::KeyPair::generate_for(&PKCS_ECDSA_P384_SHA384)`).
2. Builds a self-signed CA certificate:
   - `basicConstraints = CA:TRUE`
   - `keyUsage = keyCertSign, crlSign, digitalSignature`
   - Validity: until 2035-01-01
3. Writes `ca.key` (mode 0600) and `ca.crt`.

On subsequent starts both files are loaded from disk and the in-memory signing context is restored.

The CA is the root of trust for the entire fleet. Its public certificate (`ca.crt`) must be distributed to agent nodes before enrollment can begin.

**Source:** `fleet/controller/src/security/ca.rs` lines 73–211

## Phase 1: Agent Identity Key Generation

On first start the agent generates a long-term identity key, which is the stable cryptographic identity of the node throughout its lifetime.

1. Checks for a TPM 2.0 device at `/dev/tpmrm0` or `/dev/tpm0`. If present and usable, the identity key is generated **inside the TPM** (ECDSA P-256, persisted at owner-hierarchy handle `0x81000001`) and the private key never leaves hardware. See [tpm.md](tpm.md) for details.
2. Otherwise — no TPM, or TPM present but unusable — falls through to the file backend: if `/var/lib/policy-node-agent/identity.key` does not exist, generates a new **ECDSA P-256** keypair from `OsRng` and writes it as PKCS#8 PEM with mode **0600**.
3. Derives a stable **Node ID** = `hex(SHA-256(SubjectPublicKeyInfo DER))`. This ID is invariant across reboots and hostname changes; it is the primary identifier for the node in the controller's database and in all audit records.

The identity key is intentionally separate from the mTLS credential key used for the management channel. It functions solely as a proof-of-possession key during enrollment. Whether the in-use key is hardware-backed is exposed via `NodeIdentity::tpm_available()` and the `tpm_backed` label on `fleet_node_info`.

**Source:** `fleet/agent/src/identity/mod.rs` lines 64–86, `fleet/agent/src/identity/tpm.rs`, `fleet/agent/src/identity/file.rs` lines 32–65

## Phase 2: Bootstrapping Trust via ZTP Bundle

The agent has to verify the controller's TLS server certificate before
sending anything. It does this via a short-lived **bootstrap bundle** (see
[ztp.md](ztp.md)) carrying the controller URL, the SHA-256 of the CA cert,
and a random enrollment token. The bundle is distributed to target hosts via
the same config-management channel the operator uses for everything else and
dropped at `/etc/policy-node-agent/bootstrap.bundle`.

On the bootstrap TLS leg the agent uses a custom rustls `ServerCertVerifier`
that walks the presented chain and accepts the connection only if some cert
in the chain hashes to the pinned fingerprint. The controller's enrollment
listener includes the CA cert in its TLS chain so the agent finds the match
without any pre-distributed trust material.

The CA cert PEM is returned in `EnrollmentResponse.ca_cert_pem` and persisted
to `/var/lib/policy-node-agent/controller-ca.crt` for the post-enrollment
mTLS leg. (It cannot live in `/etc/` because the systemd unit's
`ProtectSystem=strict` + `ConfigurationDirectory=` make that path read-only
for the agent.)

The bundle's token causes the controller to auto-approve the request and
return the per-node mTLS credentials in the same response, eliminating the
operator-approval step for the common case. The bundle file is deleted on
first successful use. If the token is invalid or expired the request still
lands in `Pending` for operator triage.

If no bundle is present, the agent refuses to start and instructs the
operator to mint one.

## Phase 3: Enrollment Request (Agent → Controller, Server-TLS only)

The agent connects to the controller's enrollment gRPC port (default **7776**) using **one-way TLS**: the agent verifies the controller's server certificate against the pre-distributed CA certificate, but does not present a client certificate (it does not have one yet).

The controller's enrollment server certificate is issued by the CA at each controller startup.

Over this authenticated channel the agent submits an `EnrollmentRequest` containing:

| Field | Contents |
|---|---|
| `public_key_der` | SPKI DER encoding of the identity public key |
| `dmi_uuid` | Content of `/sys/class/dmi/id/product_uuid` (informational) |
| `csr_pem` | A PEM-encoded CSR signed by a fresh ephemeral P-256 keypair |
| `signature` | ECDSA-P256 signature over `SHA-256(csr_pem)` using the **identity key** |
| `agent_version` | Semver string |
| `hostname` | System hostname |
| `bootstrap_token` | Optional ZTP token `{token_id, secret}` from the bootstrap bundle. When present and valid the controller auto-approves; see [ztp.md](ztp.md). |

The signature over the CSR hash is the **proof of possession**: it demonstrates that the sender holds the private key corresponding to the `public_key_der` it is claiming. Without this signature anyone could submit an arbitrary public key and claim ownership.

**Source:** `fleet/agent/src/enrollment/mod.rs` lines 206–251

---

## Phase 4: Controller Validates the Enrollment Request

The controller's enrollment service calls into the node registry, which:

1. Recomputes `node_id = hex(SHA-256(public_key_der))` and uses it as the primary key.
2. Parses the submitted public key from DER: `VerifyingKey::from_public_key_der(...)`.
3. Recomputes `SHA-256(csr_pem)` and verifies the ECDSA signature — if this fails the request is rejected.
4. Checks that no node with the same `node_id` is already active.
5. Records the node as `NodeStatus::Pending` in SQLite, storing the public key, hostname, DMI UUID, and a generated `enrollment_id` (UUID).
6. Returns the `enrollment_id` and the CA certificate PEM to the agent.

**Source:** `fleet/controller/src/grpc/enrollment.rs` lines 25–73, `fleet/controller/src/node_registry/mod.rs` lines 44–124

## Phase 5: Approval

There are two paths to Active.

### 5a — Auto-approval via ZTP token (normal case)

If the agent presented a valid `bootstrap_token` in the request, the
controller atomically redeems the token (decrementing `uses_remaining` in
`enrollment_tokens`), then runs the same approval logic as 5b. The mTLS
credentials are returned in the *same* `EnrollmentResponse` (the agent does
not need to poll). See [ztp.md](ztp.md) for the token lifecycle.

### 5b — Operator approval (token rejected or absent)

When the token is invalid, expired, or exhausted the node lands in `Pending`
and the operator approves it manually via GraphQL `approveEnrollment(nodeId)`
(typically only used to investigate suspicious enrollments — the normal flow
is 5a). The controller:

1. Confirms the node is in `Pending` state.
2. Issues a new **ECDSA P-256** keypair (controller-generated, distinct from the identity key).
3. Signs a client certificate with the CA:
   - `CommonName = node_id`
   - `keyUsage = DigitalSignature`
   - `extendedKeyUsage = ClientAuth`
   - `basicConstraints = ExplicitNoCa` (the cert cannot itself sign further certs)
   - TTL = `node_cert_ttl_days` (default 90 days)
4. Stores the concatenated `key_pem + cert_pem` blob in SQLite.
5. Marks the node `Active`.

The controller generates the mTLS keypair (rather than using a CSR from the agent) to keep the identity key and the mTLS key cleanly separated. A future phase will optionally support agent-submitted CSRs so that the mTLS key can be TPM-bound and never leave the hardware.

**Source:** `fleet/controller/src/security/ca.rs` lines 115–190, `fleet/controller/src/node_registry/mod.rs` lines 150–221

## Phase 6: Agent Polls for Approval and Saves Credentials

The agent polls `CheckEnrollmentStatus` with exponential back-off:
- First 30 attempts: every 2 seconds (1 minute window)
- Thereafter: every 10 seconds

When the status is `Approved` the response contains the `key_pem + cert_pem` blob. The agent splits it at the `-----BEGIN CERTIFICATE-----` marker and writes:

| File | Mode | Contents |
|---|---|---|
| `/var/lib/policy-node-agent/controller-client.key` | 0600 | ECDSA P-256 private key (PKCS#8 PEM) |
| `/var/lib/policy-node-agent/controller-client.crt` | 0644 | Signed client certificate (PEM) |
| `/etc/policy-node-agent/controller-ca.crt` | 0644 | CA certificate (refreshed copy) |

**Source:** `fleet/agent/src/enrollment/mod.rs` lines 107–117, 254–320

## Post-Enrollment: Management Channel Security

After successful enrollment the agent connects to the controller's management gRPC port (default **7777**) using **mutual TLS (mTLS)**.

### TLS Handshake

**Agent (client side):**
```
ca_certificate   = /etc/policy-node-agent/controller-ca.crt
identity (cert)  = /var/lib/policy-node-agent/controller-client.crt
identity (key)   = /var/lib/policy-node-agent/controller-client.key
```

**Controller (server side):**
```
server identity  = ephemeral cert issued from the CA at startup
client_ca_root   = same CA, requiring and verifying a client certificate
```

Both sides authenticate each other during the TLS handshake:
- The agent verifies the controller's server certificate against the CA.
- The controller verifies the agent's client certificate against the CA.

This means a compromised or unenrolled node cannot connect to the management port at all — the TLS handshake will fail without a valid CA-signed client cert.

**Source:** `fleet/controller/src/bin/controller.rs` lines 175–206, `fleet/agent/src/controller_client/mod.rs` lines 70–105

### Application-Layer Node Validation

Even after a successful mTLS handshake the controller performs an additional application-layer check. The first message the agent sends is an `AgentHello` containing its `node_id`. The management stream handler verifies that this `node_id` is `Active` in the database. A decommissioned node whose certificate has not yet expired would be rejected at this layer.

The handler also enforces `protocol_version == PROTOCOL_VERSION` (currently 1), disconnecting any agent running an incompatible version.

**Source:** `fleet/controller/src/grpc/management.rs` lines 174–213

### Certificate Revocation

When a node is decommissioned the controller stores the certificate serial number in the `revoked_certs` SQLite table. Two layers enforce revocation:

1. **Application layer (today):** the management stream handler reads the stored `cert_serial` for the claimed `node_id` after `AgentHello` and rejects the stream if that serial is in `revoked_certs`. See `fleet/controller/src/grpc/management.rs` lines 215–240.
2. **TLS handshake layer (Phase 7):** a custom rustls `ClientCertVerifier` extracts the serial from the *presented* peer cert and rejects the handshake itself, so a stale cert cannot be used to even open a stream after re-enrollment. See Phase 7 below.

### Channel to Local policy-engine

The agent communicates with the local `policy-engine` daemon over plain HTTP on loopback (`http://127.0.0.1:8080/graphql`). No TLS or authentication is applied to this channel; it is intentionally local-only and the threat model treats the loopback interface as trusted.

## Cryptographic Primitive Summary

| Purpose | Algorithm | Notes |
|---|---|---|
| Controller CA key | ECDSA P-384 | Stronger curve for the long-lived CA key |
| Agent identity key | ECDSA P-256 | Stable across reboots; never leaves the node |
| mTLS client key | ECDSA P-256 | Issued by controller; rotated on re-enrollment |
| gRPC server cert key | ECDSA P-256 | Regenerated at each controller startup |
| Node ID derivation | `hex(SHA-256(SPKI DER))` | Stable, deterministic, no PKI dependency |
| Enrollment PoP signature | ECDSA-P256-SHA256 over `SHA-256(csr_pem)` | Proves possession of the identity private key |
| TLS runtime | rustls + ring | No OpenSSL; ring provides all primitives |
| Key serialization | PKCS#8 PEM | Used throughout for all key files |
| Certificate validity | rcgen | Rust-native X.509 certificate generation |

## Phase 7: Rotation and Renewal

The credentials produced by Phases 1–6 are not all rotated on the same cadence. This phase documents what rotates, what does not, and how.

### What Rotates

| Material | Rotation cadence | Mechanism |
|---|---|---|
| Node mTLS client cert | Renewed at ~2/3 of `node_cert_ttl_days` (≈60d of 90d default) | `RenewClientCert` RPC on the management port |
| Node mTLS client key | Every Nth renewal (`mtls_key_rotation_renewals`, default 4 ≈ ~240d) | Agent generates a fresh keypair and submits a new CSR |
| Controller gRPC server cert | Every controller boot | Re-issued from the CA in-memory |
| CA cert/key | Manual, multi-step (see *CA Rotation* below) | Dual-CA trust window |

### What Does *Not* Rotate

- **Agent identity key** — by construction. It anchors the node ID (`hex(SHA-256(SPKI DER))`); rotating it would change the node's identity and break audit continuity. The identity key only proves possession during enrollment; it is not used for the management channel.
- **Node ID** — derived from the identity key, therefore equally stable.

### Node mTLS Cert Renewal

The agent runs a background renewal task on the management channel. The task:

1. Reads `not_before` and `not_after` from `controller-client.crt` on startup.
2. Computes `renew_at = not_before + 2/3 * (not_after - not_before)`, with ±5% jitter to avoid fleet-wide thundering herd.
3. When `now >= renew_at`, generates a CSR. The key is either:
   - the **existing** `controller-client.key`, if the renewal counter has not crossed `mtls_key_rotation_renewals`; or
   - a **fresh** ECDSA P-256 keypair, otherwise (counter resets).
4. Calls `RenewClientCert(csr_pem)` on the management gRPC port, authenticated by the *current, still-valid* mTLS cert.
5. Writes the returned cert (and key, if rotated) atomically: stage `.new` → fsync → rename. Old cert remains valid until its own `not_after`, so a torn write or controller error never bricks the node.

The controller's renewal handler:

1. Extracts `node_id` from the **peer certificate's** CommonName (not from a self-reported field), guaranteeing the renewal cannot be steered to a different node.
2. Confirms the node is `Active` and its current `cert_serial` is not revoked.
3. Validates the CSR's signature and rejects any CSR whose subject CN does not match the authenticated `node_id`.
4. Signs a new cert with the CA using the same template as Phase 5b, records the new serial, and *revokes* the previous serial (so the old cert cannot be used in parallel after handoff).
5. Returns `cert_pem`. The key is *not* in the response — the agent generated it; the controller never sees it.

Failure modes:
- Renewal RPC fails and cert is within 7d of expiry → loud log + `fleet_node_cert_renewal_failures_total` metric + `cert_renewal_failing` label on `fleet_node_info`.
- Cert expires before successful renewal → agent falls back to full enrollment, which requires a fresh ZTP bundle from the operator. This is intentional: an expired cert means the renewal channel was unreachable for ≥30d and operator awareness is warranted.

### Revocation at the TLS Handshake

Phase 7 ships a custom rustls `ClientCertVerifier` that:

1. Delegates trust-chain validation to the default CA-rooted verifier.
2. After chain validation, extracts the leaf cert's serial number and looks it up in an in-memory `HashSet<Vec<u8>>` mirror of the `revoked_certs` table.
3. Rejects the handshake on a match.

The in-memory mirror is loaded once at controller boot and updated via a tokio `watch` channel each time `revoke_cert` is called in the node registry — no polling. The existing application-layer revocation check in `management.rs` stays as defense in depth: it catches the narrow window between a `revoke_cert` write and the watch-channel propagation, and it covers any future non-mTLS code path that needs the same guard.

### CA Rotation

Rotating the long-lived CA is a multi-month operation and has its own design doc: [ca-rotation.md](ca-rotation.md). At a glance:

- The controller can hold two CAs simultaneously (`ca_current`, `ca_next`) for a trust-window period (default 120d, must exceed `node_cert_ttl_days`).
- `ca_next` is distributed to agents over the management channel as a `TrustAnchorUpdate` control message; agents append it to `controller-ca.crt` after verifying it is delivered over a session authenticated by `ca_current`.
- Cutover: the controller switches `RenewClientCert` to sign under `ca_next` and serves a server cert chained to `ca_next`. The previous CA stays as a trust anchor on both sides until the last cert it signed has expired.
- Bundles minted post-cutover pin `ca_next`'s SHA-256.

Identity-key rotation and HSM-bound CAs are explicitly out of scope.

**Source:** `fleet/controller/src/security/revocation.rs` (Phase 7), `fleet/controller/src/grpc/management.rs` `RenewClientCert` handler, `fleet/agent/src/controller_client/renewal.rs`

## Enrollment Flow Diagram

```
Agent                                   Controller
  |                                         |
  |-- [first boot] --                       |
  |  generate identity keypair (P-256)      |
  |  derive node_id = hex(SHA256(SPKI))     |
  |                                         |
  |           [out-of-band]                 |
  |<-------- ca.crt (pre-distributed) ------|
  |                                         |
  |-- [server-TLS, port 7776] ------------>|
  |  EnrollmentRequest {                    |
  |    public_key_der,                      |
  |    csr_pem,                             |
  |    signature = ECDSA(identity_key,      |
  |                SHA256(csr_pem))         |
  |  }                                      |-- verify PoP signature
  |                                         |-- store as Pending
  |<-------- enrollment_id + ca.crt --------|
  |                                         |
  |  [poll CheckEnrollmentStatus]           |  [operator approves via UI/API]
  |                                         |-- generate mTLS keypair (P-256)
  |                                         |-- sign client cert (CA, 90d TTL)
  |                                         |-- store cert + key in DB
  |                                         |-- mark node Active
  |                                         |
  |<-------- key_pem + cert_pem ------------|
  |  save controller-client.key (0600)      |
  |  save controller-client.crt            |
  |                                         |
  |== [mTLS, port 7777] ==================>|
  |  present controller-client.crt         |-- verify client cert (CA)
  |  verify controller server cert (CA)    |-- verify node_id is Active in DB
  |                                         |
  |  AgentHello { node_id, proto_version } |
  |  [ongoing encrypted management stream] |
```
